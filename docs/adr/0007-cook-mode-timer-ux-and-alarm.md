# 0007 — Cook Mode: единый редактор таймера и системное завершение

Статус: Accepted, 2026-10-09 (заменяет 0006 в части создания таймера и завершения)

## Контекст

После первой проверки на устройстве в Cook Mode накопилось три проблемы:

- время создавалось двумя разными путями: готовый setup под текстом шага и
  отдельный «+ Таймер» снизу — пользователь видел два одинаковых контрола;
- при нескольких найденных временах и диапазоне показывались отдельные кнопки
  на каждое значение;
- завершение таймера опиралось на composable/ViewModel: вибрация шла из UI и
  «иногда вообще не происходила», а при background/выключенном экране сигнала
  не было вовсе. Кухонному таймеру нужен системный механизм.

Парсер времени (`CookTimerParser`) уже есть и менять его не требуется.

## Решение

- **Одна точка создания.** Под текстом шага нет контролов таймера. Таймер всегда
  создаётся через «+ Таймер» в нижней зоне: он раскрывает инлайн-редактор
  `− 15:00 + ▶`, а текст действия меняется на «Отмена / Cancel». Отмена закрывает
  редактор и ничего не запускает. Парсер лишь задаёт начальное значение:
  первый `suggestion` шага (диапазон → нижняя граница), иначе 05:00.
- **Состояние редактора — в ViewModel** (`TimerEditorState`), не в composable:
  правило «Cancel ничего не создаёт, Start создаёт ровно один таймер» юнит-тестируется
  без Compose. Поле `session` открывает новую сессию правки, при этом переживая
  смену конфигурации.
- **Завершение — системное событие.** На запуск таймера планируется
  `AlarmManager`-будильник, который поднимает `BroadcastReceiver`; тот показывает
  notification и даёт вибрацию. Это работает при свёрнутом приложении, выключенном
  экране и когда Cook Mode не на переднем плане. Foreground service не нужен:
  работы в момент срабатывания почти нет.
- **Планировщик за интерфейсом** `CookTimerScheduler` (domain): ViewModel зависит
  от него, реальная реализация `CookTimerAlarms` — только на Android. Это даёт
  тестируемость правил (fake scheduler) и не тащит Android в unit-тесты.
- **Стабильные id и независимость.** У активного таймера монотонный id, который не
  переиспользуется после удаления (`ActiveTimers.nextId` — часть состояния, а не
  вычисляется из списка). Alarm и notification адресуются одним request code и
  data-URI `mealio://cook-timer/<id>`, поэтому schedule/cancel каждого таймера
  независимы. Remove и Restart отменяют прежний alarm; Restart заводит таймер с
  новым id и, значит, новым alarm.
- **Двойного срабатывания нет.** Единственный источник — системный alarm; UI лишь
  рисует остаток из deadline. `refresh()` больше не отменяет alarm у истёкших
  таймеров: отмена прежнего alarm происходит только при remove/restart, так что
  поздний inexact-alarm всё равно доставит уведомление.
- **Notification channel** создаётся один раз с `IMPORTANCE_HIGH`, alarm-звуком и
  паттерном вибрации: с Android 8 звук и вибрация берутся из канала, а не из
  builder. Текст: «Таймер завершён / Шаг N» (EN: «Timer finished / Step N»).
  Тап открывает Mealio; отдельного deep link в Cook Mode нет — состояние
  восстанавливается из сохранённого deadline.
- **Разрешения по минимуму.** `VIBRATE`; `POST_NOTIFICATIONS` запрашивается
  контекстно при входе в Cook Mode (не при старте приложения);
  `SCHEDULE_EXACT_ALARM` — специальный доступ, запрашивается один раз при первом
  запуске таймера, только если его нет. Без него alarm ставится inexact-API
  (`setAndAllowWhileIdle`) и может сработать с задержкой, но не теряется.

## Отвергнутые альтернативы

- **WorkManager для countdown** — не его задача: минимальный интервал ~15 минут,
  будильник на минуту он не заменяет.
- **Foreground service** — нужен для долгой работы, а не для «дойти до нуля и
  пикнуть»; лишний шум и постоянное уведомление.
- **Вибрация/звук из Compose или ViewModel** — не работает при background и
  выключенном экране, и «иногда не срабатывает» именно поэтому.
- **Две кнопки на диапазон (4 и 5 минут)** — пользователь всегда может нажать «+»;
  лишний контрол.
- **Deep link из уведомления прямо в Cook Mode** — непропорционально сложно для
  этой задачи, состояние и так восстанавливается по deadline.

## Последствия

- Парсер больше не автозапускает таймер: его результат — только начальное значение
  редактора.
- Один контрол создания вместо двух; заголовка «Таймеры / Timers» в нижней зоне нет.
- Без разрешения на exact alarms время срабатывания не гарантировано точно —
  компромисс, зафиксированный сознательно (см. раздел «Разрешения»).
- Reboot и force-stop по-прежнему вне scope: alarm не переживает перезагрузку.
